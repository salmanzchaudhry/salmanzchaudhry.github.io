Architecture

The Medallion Model

Medallion Architecture organizes data into three progressive layers. Each layer has a clear job: Bronze stores data exactly as it arrives from the source. Silver cleans and standardizes it. Gold structures it for business use. This separation makes it easy to trace any number in a report all the way back to raw source data.

🥉

Bronze Layer

Raw Ingestion

  • Load source data exactly as received
  • No transformations applied
  • Preserves full audit trail
  • Stored proc handles incremental loads
  • Source system tables replicated here
🥈

Silver Layer

Cleansed & Standardized

  • Null handling and default fills
  • Data type standardization
  • Duplicate removal logic
  • String trimming and normalization
  • Date format consistency enforced
  • Business rule validations applied
🥇

Gold Layer

Star Schema Model

  • Fact table with foreign keys
  • Dimension tables (Customer, Product, Date)
  • Surrogate keys replace natural keys
  • Optimized for analytical queries
  • Data catalog documents every column

Key Patterns from the Build

Three patterns drive the logic across all six scripts. The stored procedure pattern keeps the load process repeatable and atomic. The cleansing pattern handles the most common data quality issues. The surrogate key pattern prepares dimensions for a clean Star Schema join.

Bronze — Incremental Load Stored Procedure

CREATE OR ALTER PROCEDURE bronze.load_crm_customers
AS
BEGIN
    -- Truncate and reload (full refresh pattern)
    TRUNCATE TABLE bronze.crm_customers;

    INSERT INTO bronze.crm_customers (
        customer_id, first_name, last_name,
        email, create_date, source_system
    )
    SELECT
        id, fname, lname,
        email_addr, created_at, 'CRM'
    FROM source.raw_customers;

    -- Log row count for monitoring
    PRINT 'Bronze load complete: '
          + CAST(@@ROWCOUNT AS VARCHAR) + ' rows';
END;

Silver — Data Cleansing Transformations

INSERT INTO silver.customers
SELECT
    customer_id,

    -- Trim whitespace and normalize case
    TRIM(UPPER(first_name))                          AS first_name,
    TRIM(UPPER(last_name))                           AS last_name,

    -- Replace nulls with default value
    ISNULL(email, 'no_email@unknown.com')             AS email,

    -- Standardize date format
    CAST(create_date AS DATE)                        AS create_date,

    -- Flag duplicates for review
    ROW_NUMBER() OVER (
        PARTITION BY email
        ORDER BY create_date DESC
    )                                                  AS row_rank

FROM bronze.crm_customers
WHERE customer_id IS NOT NULL;

Gold — Surrogate Key Pattern for Dimension Table

-- Surrogate key replaces natural key as primary key
-- Enables clean joins even when source system IDs change
INSERT INTO gold.dim_customers (
    customer_key,        -- surrogate key (identity)
    customer_id,         -- natural key (from source)
    first_name,
    last_name,
    email,
    create_date
)
SELECT
    ROW_NUMBER() OVER (ORDER BY customer_id) AS customer_key,
    customer_id,
    first_name,
    last_name,
    email,
    create_date
FROM silver.customers
WHERE row_rank = 1;  -- deduplicated: keep most recent record

Key Learnings

What This Project Taught Me

The most valuable thing I learned was why separating raw storage from clean storage matters in practice. Before this project, I had been writing queries that cleaned and queried data at the same time. Building three explicit layers forced me to think about each concern independently, and it made debugging far easier because I always knew exactly where to look when something broke.

Writing stored procedures for each layer was also a shift. Instead of running scripts manually and hoping they run in order, the pipeline becomes something you can actually schedule and trust. That repeatability is what makes a data warehouse usable rather than just a one-time exercise.
